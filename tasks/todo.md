# iPhone でのボカシ不具合（数値変遷とズーム時の再計算）

## 要求

1. iPhone でボカシ・モザイクの数値変遷がおかしいまま
2. ボカシを置いたあとキャンバスを拡縮すると、ボカシの内容が更新されてしまう

## 原因

どちらも **WebKit（iOS Safari）で使われるフォールバックのボカシ**が原因だった。
WebKit は `ctx.filter` を持たないため、縮小・拡大による代替実装が動く。

```ts
const factor = Math.max(2, Math.min(96, radius * 1.5))
const cols = Math.max(1, Math.round(width / factor))
```

縮小率をぼかし半径に連動させていたため、

- 半径が少し動くだけで `cols` が整数で跳ぶ → **強さの変化が段階的・非単調**
- `min(96, …)` の上限に張り付くと `cols` がキャンバス幅に比例する →
  **表示倍率を変えるとぼかしの粗さが変わる**

Chrome はネイティブのぼかしを使うので、この症状は表面化していなかった。

### 実測（WebKit・修正前）

| 強さ | 5 | 35 | 55 | 60 | 65 | 100 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| ディテール量 | 2.505 | 0.312 | 0.225 | 0.185 | 1.072 | 1.000 |

増加 9 回・同値 4 回。**強さ 100 が 55〜60 より弱い**という逆転まで起きていた。

## レビュー

### 対処

縮小率を **半径から切り離して固定（0.3）** し、縮小後のバッファに移動平均（box blur）を掛けてから
引き伸ばす方式に変えた。

- 縮小後のサイズも box blur の半径も表示倍率に比例するので、**倍率を変えても見た目が変わらない**
- 半径が連続的に効くので、強さの変化がなめらか
- 移動平均を 3 回重ねてガウシアンに近づける。半径は整数しか取れないため、
  パスごとに 1 だけ大きくして実効半径の刻みを 1/3 にした
- ブロック境界が出ないので、以前の縮小・拡大方式より見た目の品質も上がった

### 実測（修正後）

| | 強さ 5 | 100 | 増加した回数 |
| --- | ---: | ---: | ---: |
| ボカシ（WebKit） | 0.408 | 0.167 | **0** |

ズーム時の安定性（ディテール量の変化。0 なら拡縮しても内容が変わっていない）:

| | 2 倍 | 4 倍 | 全体表示に戻す |
| --- | ---: | ---: | --- |
| ボカシ（WebKit） | 0 | 0 | 復元 |
| モザイク（WebKit） | +0.001 | +0.001 | 復元 |
| ボカシ（Chrome） | -0.002 | -0.002 | 復元 |
| モザイク（Chrome） | 0 | 0 | 復元 |

### モザイクについて

WebKit の測定値は Chrome とほぼ同一で、**WebKit 固有の問題ではなかった**（前回の領域基準への
変更で改善済み）。残る振れはサンプル位置とセル境界の位相によるもので、セル数が整数である以上の
構造的な限界。強さ→セル数は単調に減っている（例: 強さ 58 で 21 セル、59 で 20 セル）。

### バンドルサイズ（gzip）

23.63KB → **24.00KB**（上限 25KB、残り 1.0KB）。

### 性能

box blur は JS ループなので、処理量は縮小後のピクセル数に比例する。
表示中は DPR 2 でも 540×360 程度（6 スキャンで約 117 万回、十数 ms）。
原寸書き出し時は画像サイズに比例するが 1 回きりなので許容範囲。
